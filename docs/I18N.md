# 다국어(i18n)

서드파티 템플릿이 b.stage 사용자 언어에 맞춰 텍스트를 표시하는 방법을 정리한다. 세 개의 훅과 한 개의 CLI 명령으로 구성된다.

상세 API 시그니처는 [API_REFERENCE.md](./API_REFERENCE.md)를 참고한다.

## 어떤 훅을 쓰나 (결정 트리)

| 필요                                     | 훅                              | 비고                                                  |
| ---------------------------------------- | ------------------------------- | ----------------------------------------------------- |
| 현재 언어 코드만                         | `useLocale()`                   | `{ current }`. 가볍고 fetch 없음                      |
| **템플릿 자체 문구**를 다국어로          | `useMessages(messages)`         | 직접 정의. 키 타입은 TS 추론(codegen 불필요)          |
| **플랫폼 공용 문구**(`Bxxxxx`) 재사용    | `useBstageTranslations()`       | `{ current, t, tNode, ready }`. CDN/플랫폼 사전 fetch |
| 그중 **링크·강조가 든 문구**(`<0>…</0>`) | `useBstageTranslations().tNode` | `t()`로 쓰면 태그가 글자로 보인다                     |

- 대부분의 템플릿은 **자기 문구가 주력 → `useMessages`** 를 쓴다.
- 플랫폼과 버튼 라벨 등을 **통일**하고 싶을 때만 `useBstageTranslations`.
- 두 훅은 양자택일이 아니다 — 실전에서는 **한 컴포넌트에서 병용**하는 것이 일반적이다([혼용 패턴](#혼용-패턴--usemessages--usebstagetranslations) 참조).
- 세 훅 모두 언어 변경(리로드 없는 SPA 전환)에 **reactive**하다.
- 세 훅 모두 **`BstageLocaleProvider` 안에서** 호출해야 한다(아래) — 밖에서 호출하면 throw.

## BstageLocaleProvider — 로케일 대상 (필수)

로케일 훅은 **반드시 `BstageLocaleProvider` 하위에서** 호출한다. 이 Provider가 `target`으로 "어느 b.stage 런타임의 로케일을 읽을지" 결정한다.

- **유저단 템플릿**: `target` 생략(`'user'`). `<html lang>`(1차) → `bmf_bstage_lang` 쿠키.
- **어드민 임베드 템플릿**: `target="admin"`. `bmf_mybstage_locale` 쿠키(1차) → `<html lang>`. 어드민은 `<html lang>`을 SSR 기본값으로 고정(런타임 미갱신)해 신뢰할 수 없기 때문.

훅은 **Provider 하위**에서 호출해야 하므로, 보통 훅을 쓰는 부분을 자식 컴포넌트로 분리한다.

```tsx
import { BstageLocaleProvider, useMessages } from '@bstage-sdk/react'

const messages = { ko: { title: '내 티켓' }, en: { title: 'My Tickets' } }

const Body = () => {
  const t = useMessages(messages) // Provider의 target에 맞춰 동작
  return <h1>{t('title')}</h1>
}

// 유저 템플릿 — target 생략
const Widget = () => (
  <BstageLocaleProvider>
    <Body />
  </BstageLocaleProvider>
)

// 어드민 템플릿
const AdminWidget = () => (
  <BstageLocaleProvider target="admin">
    <Body />
  </BstageLocaleProvider>
)
```

`target`은 `bstage i18n pull --target user|admin`의 `--target`과 동일 축이다(번역 사전 대상 + 로케일 신호 대상).

## useLocale — 현재 언어

```tsx
import { useLocale } from '@bstage-sdk/react'

const { current } = useLocale() // 'ko' | 'en' | 'ja' | 'zh-CN' | 'zh-TW' | 'es' | 'vi'
```

`target='user'`(기본)은 `<html lang>`을 읽고 MutationObserver로 변경을 감지한다. 유저 플랫폼가 언어 변경 시 `<html lang>`을 갱신하므로 플랫폼 추가 작업 없이 동작한다. `target='admin'`은 `bmf_mybstage_locale` 쿠키를 1차로 읽는다([위](#bstagelocaleprovider--로케일-대상-필수)). 신호가 없으면 기본 로케일로 fallback한다.

## useMessages — 템플릿 자체 문구

플랫폼 번역 시스템에 없는 **자기 문구**를 로컬 코드로 다국어 등록한다.

```tsx
import { useMessages } from '@bstage-sdk/react'

const messages = {
  ko: { title: '내 티켓', greet: '{{name}}님 환영합니다' },
  en: { title: 'My Tickets', greet: 'Welcome {{name}}' },
}

function Panel() {
  const t = useMessages(messages)
  return <h1>{t('title')}</h1> // 'title' 자동완성, 오타 컴파일 에러
}
```

- 키 타입은 **객체 리터럴에서 TS가 추론** → codegen 불필요, 자동완성·타입체크.
- `{{token}}` 보간. 현재 로케일 사전이 없으면 기본 로케일 → 첫 사전 fallback, 키가 없으면 키 문자열 반환.
- 완전 로컬 — 네트워크·플랫폼과 무관, standalone 동작.

## useBstageTranslations — 플랫폼 공용 문구

플랫폼의 공용 번역 사전(`Bxxxxx` → 문자열)을 재사용한다.

```tsx
import { useBstageTranslations } from '@bstage-sdk/react'

function ApplyButton() {
  const { current, t, ready } = useBstageTranslations()
  if (!ready) return null // 로드 전 코드 노출 방지
  return <button>{t('B00001')}</button> // → "적용하기"
}
```

- 현재 로케일 사전을 fetch하고 로케일 변경 시 재로드(로케일별 캐시). `{{token}}` 보간 — `t('C00180', { str1: 3 })` → `"3시간 남음"`.
- 현재 언어 코드(`current`)도 함께 반환 → 이 훅 하나로 언어·번역 모두 얻는다.
- 키가 opaque(`B00001`)이므로 **타입 안전·자동완성은 `bstage i18n pull` codegen이 채운다**(아래).
- 사전은 **TMS가 배포한 CDN**에서 받는다(아래 [사전 출처](#사전-출처)). 시스템(`user`/`admin`)은 `BstageLocaleProvider`의 `target`이 정하므로 추가 설정이 없다.

## 링크·강조가 든 문구 — `tNode`

플랫폼 사전에는 `<0>…</0>` 표기로 링크·강조 자리를 남긴 문구가 있다. `t()`는 문자열을 반환하므로 그 자리에 **`<0>`이 글자로 보인다** — 이 문구는 `tNode`로 렌더한다.

```tsx
const { t, tNode, ready } = useBstageTranslations()
if (!ready) return null

// S00417: "서비스 이용에 궁금한 사항이 있다면, <0>‘MY > 고객센터’</0> 를 통해서 문의해 주세요"
return <p>{tNode('S00417', { tags: { 0: <a href="/my/cs" /> } })}</p>
```

- `tags`의 키가 태그 인덱스(`<0>`의 0)다. 엘리먼트를 넘기면 그 조각을 감싸고, **안 넘기면 내용만 렌더한다**(문구가 사라지지 않는다). dev에서는 누락 시 콘솔 경고가 뜬다.
- 보간을 함께 쓴다 — `tNode('S00739', { params: { str: '쇼' }, tags: { 0: <b /> } })`.
- 한 문구에 인덱스가 둘 이상인 경우가 있다(`<0>…</0>` + `<1>…</1>`) → `tags: { 0: <b />, 1: <a href="…" /> }`.
- **문자열이 필요한 자리**(`placeholder`·`aria-label`·`title`)는 계속 `t()`를 쓴다.
- 리치텍스트 문구를 `t()`로 쓰면 dev 콘솔이 `tNode`를 쓰라고 경고한다.

> 파라미터 값에 `<0>`이 들어 있어도 태그로 해석되지 않는다(조각을 나눈 뒤 보간하므로). 소비자가 넘긴 값이 마크업이 되는 일은 없다.

## 사전 출처

`useBstageTranslations`가 읽는 사전은 **TMS가 배포한 CDN JSON**이다. 버전 포인터(`latest.json`)를 먼저 보고 그 버전 경로에서 사전을 받으므로, TMS가 새로 배포하면 플랫폼 앱 배포 주기와 무관하게 반영된다.

```
cdn.static.bstage.in/static/i18n/{phase}/{system}[/{tier}]/latest.json
  → {version, cdnPath}  →  .../{version}/{lang}/translation.json
```

기본값으로 그대로 동작하므로 **대부분의 템플릿은 아무 설정도 하지 않는다.**

- `phase` — hostname에서 판정한다(`.dev.`·`.qa.`·`sandstage.in`, 그 외 `real`). `bstage dev`는 `--phase`를 주입하므로 로컬도 맞는다.
- `system` — `BstageLocaleProvider`의 `target`(`user`\|`admin`).
- `tier` — 기본 `inhouse`.
- `fallbackChain` — 미번역 키에서 대신 볼 순서. 기본 `['en', 'ko']`.

바꿔야 할 때만 부팅 시 한 번 호출한다.

```ts
import { configureBstageI18n } from '@bstage-sdk/core'

configureBstageI18n({ tier: 'mnetplus' }) // origin·phase·system·tier·fetch 지정 가능
```

> **미번역이면 폴백 사전을 본다** — 사전에는 키는 있고 **값만 빈 문자열**인 항목이 있다(어드민은 일부 로케일이 대부분 그렇다). 그런 키를 만나면 폴백 사전(`en` → `ko`)을 **그때 추가로 받아** 채운다. 번역이 다 있는 로케일에서는 추가 요청이 없다.

> **CDN이 죽어도 문구가 뜬다** — 성공한 응답을 Cache Storage에 남겨두고, 실패 시 그것으로 렌더한다. **번들 크기는 늘지 않는다.** 그 오리진에서 한 번도 성공한 적 없는 첫 방문이 장애와 겹치면 키가 노출된다.

> **인증 fetch를 쓰지 않는다** — 번역 CDN은 공개 호스트다. 플랫폼이 주입하는 `__bstage_fetch__`는 URL을 가리지 않고 `Authorization`(+ dev/qa는 CF Access) 헤더를 붙이는데, 그러면 크로스 오리진 요청이 CORS preflight 대상이 되고 이 CDN은 `OPTIONS`에 403을 준다. 그래서 사전은 기본 `fetch`로 받는다(`BstageClient`는 게이트웨이를 부르므로 그쪽은 그대로 인증 fetch를 쓴다).

> **알려진 오차** — `tier`는 런타임에 알 수 있는 신호가 없다(플랫폼은 서버에서 HTTP 헤더로 받는다). 그래서 기본 `inhouse`이며, hiand·flo·mnetplus 스페이스에 올라간 위젯은 위처럼 지정하지 않으면 inhouse 사전을 본다.

> **플랫폼 런타임과 독립이다** — 이 출처는 b.stage 플랫폼 앱이 자기 화면을 그릴 때 읽는 경로와 **의도적으로 분리**돼 있다. 지금은 같은 문구가 나오지만, TMS가 테넌트를 지원하면 갈라진다. "플랫폼과 다른 사전"은 버그가 아니다.

## 혼용 패턴 — useMessages + useBstageTranslations

실제 템플릿에서는 두 훅을 **한 컴포넌트에서 함께 쓰는 것**이 가장 일반적인 구성이다. 문구를 두 부류로 나눠 각각 맞는 훅으로 처리한다.

- **도메인 특화 문구** (페이지 제목, 안내문 등 이 템플릿에만 있는 문구) → `useMessages`
- **플랫폼 공용 문구** (저장·취소·적용하기 등 플랫폼 UI와 통일할 라벨) → `useBstageTranslations`

```tsx
import { useMessages, useBstageTranslations } from '@bstage-sdk/react'

const messages = {
  ko: { pageTitle: '랭킹투표 관리', empty: '등록된 투표가 없습니다' },
  en: { pageTitle: 'Ranking Poll Admin', empty: 'No polls yet' },
}

function AdminPanel() {
  const t = useMessages(messages) // 도메인 특화 문구
  const { t: pt, ready } = useBstageTranslations() // 플랫폼 공용 문구

  if (!ready) return null
  return (
    <div>
      <h1>{t('pageTitle')}</h1> {/* 커스텀: 랭킹투표 관리 */}
      <p>{t('empty')}</p> {/* 커스텀: 등록된 투표가 없습니다 */}
      <button>{pt('B00001')}</button> {/* 공용: 적용하기 */}
    </div>
  )
}
```

- 이름 충돌은 `const { t: pt } = ...`처럼 구조 분해 별칭으로 푼다.
- 문구를 새로 추가할 때는 **플랫폼 키부터 찾아보고**(`src/bstage-i18n.ts`에서 원문 검색), 매칭되는 키가 있으면 공용 키를, 없으면 `useMessages`에 추가한다. 공용 키가 있는 문구를 `useMessages`에 중복 정의하면 플랫폼이 번역을 고쳐도 템플릿에 반영되지 않는다.

## `bstage i18n pull` — 타입 안전 키 (codegen)

`useBstageTranslations`의 `Bxxxxx` 키를 자동완성·검증 가능하게 하려면 codegen을 돌린다. CDN에서 최신 번역을 직접 받아(인증 불필요) 타입 모듈과 로컬 캐시를 생성한다.

```bash
bstage i18n pull                 # 기본: --phase real --target user --tier inhouse --ref ko
bstage i18n pull --phase dev     # dev/qa 번역으로 받기
bstage i18n pull --target admin  # 어드민 플랫폼 번역(Axxxxx 키)으로 받기
```

> **유저 vs 어드민**: 유저 슬롯 템플릿은 `--target user`(기본, `Bxxxxx` 키), 어드민 슬롯 템플릿은 `--target admin`(`Axxxxx` 키)을 쓴다. 로케일 코드는 양쪽이 동일하고, 런타임 경로는 `system` 세그먼트만 갈린다(`static/i18n/{phase}/{user|admin}/...`). **현재 언어 감지 신호도 다르다** — 유저는 `<html lang>`, 어드민은 `bmf_mybstage_locale` 쿠키([BstageLocaleProvider](#bstagelocaleprovider--로케일-대상-필수)). 런타임 `--target`도 Provider의 `target`과 같은 축이다. 한 프로젝트에서 두 시스템을 모두 쓰면 `--out`으로 타입 파일을 분리한다.

생성물:

- **`src/bstage-i18n.ts`** (커밋) — `TranslationKeyRegistry`를 declaration merging으로 보강해 `t()`의 키를 좁히고, 각 키에 원문을 JSDoc로 붙여 **자동완성 시 의미 확인 + 코드 내 원문 검색**을 제공한다. 한 번 import하면 타입이 적용된다.

  ```tsx
  import '../bstage-i18n' // 어딘가에서 한 번 import → t() 키가 좁혀짐
  ```

- **`.bstage/i18n/{target}/{lng}.json`** (gitignore) — 타입 생성의 입력이자 원문 검색용 스냅샷. `target`별로 나뉘어 user·admin을 함께 받아도 서로 덮어쓰지 않는다. 재생성 가능. **런타임은 이 캐시를 읽지 않는다** — dev에서도 프로덕션과 같은 경로(TMS CDN)를 탄다.

**워크플로 요약**: 플랫폼 문구를 쓰려면 → `bstage i18n pull` 실행 → 생성된 `src/bstage-i18n.ts`를 import → `useBstageTranslations().t('B…')` 자동완성.

## 로컬 개발에서 언어 전환 테스트

`bstage dev`는 dev 전용 전역 함수를 주입한다(빌드 산출물 미포함):

```js
__bstage_setLocale__('en') // <html lang> + 쿠키 갱신 → 세 훅 모두 reactive하게 갱신
```

콘솔에서 호출해 언어별 렌더를 검증할 수 있다. 유저(`bmf_bstage_lang`)·어드민(`bmf_mybstage_locale`) 쿠키를 모두 갱신하므로 `BstageLocaleProvider target="admin"`로 감싼 어드민 템플릿도 동일하게 검증된다.

## 함정 정리

- 플랫폼 키(`Bxxxxx`)는 **opaque** — 의미는 호버(JSDoc) 또는 `src/bstage-i18n.ts`에서 원문 검색으로 확인한다.
- `useBstageTranslations`의 `ready`가 `false`인 동안 `t`는 키 문자열을 반환 → 코드 노출이 싫으면 렌더를 가드한다.
- **`t(key, ...)`의 2번째 인자는 fallback이 아니라 보간 파라미터(객체)다.** `t('A03261', '저장되었습니다')`처럼 fallback 문자열을 넘기면 그 문자열은 조용히 무시되고, `A03261`이 플랫폼 사전에 다른 뜻(예: "초대 링크가 유효하지 않습니다")으로 등록돼 있으면 **그 값이 렌더된다**. 새 문구는 플랫폼 키를 재사용하지 말고 `useMessages`(로컬 키)로 정의한다. dev 모드에서 이 오용은 `[bstage]` 콘솔 경고로 잡힌다.
- **같은 문구의 소스는 하나** — 플랫폼 공용 키가 있는 문구를 `useMessages`에 복사해 덮어쓰지 않는다(플랫폼 번역 수정이 템플릿에 반영되지 않게 됨). 두 훅을 한 컴포넌트에서 병용하는 것 자체는 정상 패턴이다([혼용 패턴](#혼용-패턴--usemessages--usebstagetranslations)).
